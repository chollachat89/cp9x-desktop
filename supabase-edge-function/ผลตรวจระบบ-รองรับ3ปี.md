# ผลตรวจระบบ CP9X — รองรับข้อมูล 2-3 ปีได้ไหม

ตรวจจากโค้ดจริงทั้ง `index.ts` (ฝั่งเซิร์ฟเวอร์) และ `index.html` (ฝั่งแอป) เมื่อ 8 กันยายน 2026 · เวอร์ชัน v1.0.56

## สรุปสั้นที่สุด

**ขนาดข้อมูลไม่ใช่ปัญหา — วิธีที่โค้ดอ่านข้อมูลต่างหากที่เป็นปัญหา**

ประเมินจากอัตราจริง (เดือนสิงหาคม 2026 มีเปิดงาน 195 แถว) ครบ 3 ปีจะได้ราว **50,000 แถวทั้งระบบ** ซึ่งสำหรับ Postgres ถือว่า *เล็กมาก* ไม่ใช่ระดับที่ต้องกังวลเลย

แต่มี **3 เรื่องที่ต้องแก้** ไม่งั้นจะเจอปัญหาจริง และ **1 เรื่องอาจพังอยู่แล้วตอนนี้**

| # | เรื่อง | ความรุนแรง | เกิดเมื่อไหร่ |
|---|---|---|---|
| 1 | ข้อมูลหายเงียบ ๆ เพราะเพดาน "Max rows" | 🔴 สูงสุด | **อาจเกิดอยู่แล้ววันนี้** |
| 2 | ตารางหลักไม่มีดัชนี (index) เลย | 🟠 สูง | ค่อย ๆ ช้าลง เห็นชัดปีที่ 2 |
| 3 | ดึงทั้งตารางมาเพื่อใช้ข้อมูลนิดเดียว | 🟠 สูง | เห็นชัดปีที่ 1-2 |
| 4 | ไฟล์ใน Storage ไม่เคยถูกลบ ไม่จำกัดขนาด | 🟡 กลาง | ราว 10 GB ที่ 3 ปี |
| 5 | วันที่เก็บเป็นข้อความ ไม่ใช่ชนิดวันที่ | 🟡 กลาง | เป็นต้นตอของข้อ 3 |

## 🔴 1. ข้อมูลหายเงียบ ๆ เพราะเพดาน "Max rows"

**นี่คือเรื่องที่ต้องเช็คก่อนเพื่อนวันนี้เลย**

Supabase มีค่าตั้งชื่อ **Max rows** ที่ `Settings → API` = เพดานจำนวนแถวสูงสุดที่ API จะคืนได้ในครั้งเดียว ถ้าข้อมูลเกินเพดาน API จะ**คืนมาแค่เท่าเพดานแล้วจบ ไม่ขึ้น error อะไรเลย** โค้ดจึงคิดว่าได้ข้อมูลครบแล้ว

**ระบบนี้เคยโดนปัญหานี้มาแล้ว** — มีคอมเมนต์ทิ้งไว้ในโค้ดเองที่ `getOpenIssuesList`:

> *"เดิม limit(1000) ทำให้พอข้อมูลเกิน 1000 แถว รายการเก่า ๆ จะหายไปจากหน้าเว็ป (แต่ยังอยู่ครบใน Supabase จริง)"*

ตอนนั้นแก้ด้วยการเปลี่ยนเป็น `limit(20000)` เฉพาะ 2 จุด แต่**ยังเหลืออีก 41 จุดในโค้ดที่ไม่ได้ใส่ลิมิตอะไรเลย** ในนั้น **15 จุดดึงทั้งตารางโดยไม่มีเงื่อนไขกรองใด ๆ**

จุดที่กระทบผู้ใช้โดยตรง:

| ฟังก์ชัน | ดึงอะไร | ถ้าโดนตัด จะเห็นอาการยังไง |
|---|---|---|
| `getBillingRoundOptions` | ทุกแถวใน billing_documents | รายชื่อรอบบิลใน dropdown ขาดไปเฉย ๆ |
| `getBillingRoundsHistory` | ทุกแถวใน billing_documents | ยอดเงินในประวัติรอบบิล**น้อยกว่าความจริง** |
| `getCompletedBillingRounds` | ทุกแถวที่ตัดบิลแล้ว | งานที่เสร็จสิ้นหายไปบางรอบ |
| `computeJobStatusReportRows` | 4 ตารางเต็ม ๆ พร้อมกัน | รายงานสถานะนับงานผิด |
| `generateBillingRound` (โหมดช่วงวันที่) | ทุกแถวใน close_issues | **จับคู่วางบิลได้ไม่ครบ = เก็บเงินไม่ครบ** |
| แผนที่ชื่อสาขา | ทุกแถวใน branches | ชื่อสาขาบางสาขาว่างเปล่า |

⚠ เรื่องที่น่าห่วงที่สุดคือแถวสุดท้าย — ทะเบียนสาขาในไฟล์ที่ให้มามี **2,257 แถว** ถ้าตาราง `branches` ในระบบมีจำนวนใกล้เคียงกันและ Max rows ตั้งไว้ที่ 1,000 แปลว่า**สาขากว่าครึ่งไม่มีชื่อในตารางวางบิลอยู่แล้วตอนนี้**

**สิ่งที่ต้องทำทันที:** เข้า `Settings → API` ดูค่า **Max rows** แล้วบอกกลับมาว่าเท่าไหร่ — ค่านี้ตัวเดียวเปลี่ยนความรุนแรงของทั้งหัวข้อนี้

- ถ้า **1,000** → มีจุดพังอยู่แล้วหลายจุด ต้องแก้ด่วน
- ถ้า **สูงกว่ามาก** (เช่น 100,000) → ยังไม่พังตอนนี้ แต่ควรแก้ให้ไม่ต้องพึ่งค่านี้ เพราะเป็นค่าที่ใครก็เผลอเปลี่ยนได้

## 🟠 2. ตารางหลักไม่มีดัชนี (index) เลย

ค้นในไฟล์ SQL ทั้งหมดของโปรเจกต์ เจอคำสั่งสร้างดัชนีแค่ **5 ตัว** และไม่มีตัวไหนอยู่บนตารางหลักเลย:

| ตาราง | โค้ดเรียกใช้กี่จุด | ดัชนีที่พบ |
|---|---|---|
| `billing_documents` | **28 จุด** | ❌ ไม่มี |
| `pm_billing_documents` | 15 จุด | มี 1 (round_no) |
| `open_issues` | 14 จุด | ❌ ไม่มี |
| `pause_records` | 13 จุด | ❌ ไม่มี |
| `close_issues` | 11 จุด | ❌ ไม่มี |
| `job_form_submissions` | 10 จุด | มี 1 (เพิ่งเพิ่ม v1.0.56) |
| `branches` | 4 จุด | ❌ ไม่มี |

ไม่มีดัชนี = ทุกครั้งที่ค้นด้วยเลขงาน Postgres ต้องไล่อ่านทุกแถวในตาราง ตอนนี้ข้อมูลน้อยเลยไม่รู้สึก แต่พอถึงปีที่ 2-3 การกดปุ่มเดียวอาจยิงคำสั่งค้นหาหลายสิบครั้ง แต่ละครั้งไล่อ่านหมื่นแถว

> หมายเหตุ: ตรวจจากไฟล์ SQL ในโปรเจกต์เท่านั้น ถ้าเคยสร้างดัชนีผ่านหน้าเว็บโดยตรงจะไม่ปรากฏในนี้ — **บล็อก 4** ในไฟล์ตรวจสุขภาพจะบอกความจริงจากฐานข้อมูลเอง

**แก้แล้ว:** ไฟล์ `เพิ่มดัชนี-รองรับ3ปี.sql` เพิ่มดัชนี 18 ตัวให้ครบทุกตารางหลัก รวม partial index สำหรับ "งานที่ยังไม่ตัดบิล" ซึ่งทำให้ข้อมูลเก่าที่สะสมไว้ 3 ปีไม่ถ่วงหน้าจอที่ใช้ทุกวันเลย

การเพิ่มดัชนี**ไม่แก้ ไม่ลบ ไม่เปลี่ยนข้อมูลใด ๆ** ลบทิ้งได้ทุกเมื่อ

## 🟠 3. ดึงทั้งตารางมาเพื่อใช้ข้อมูลนิดเดียว

ตัวอย่างชัดที่สุดคือ `getBillingRoundOptions` — ฟังก์ชันที่ถูกเรียก**ทุกครั้งที่เปิดหน้าตารางวางบิล**:

```
ดึง: ทุกแถวใน billing_documents  (3 ปี ≈ 27,000 แถว)
ใช้: แค่เลขรอบบิลที่ไม่ซ้ำกัน     (≈ 150 ค่า)
```

ทิ้งไป 99.5% ของสิ่งที่ดึงมา และเป็นการโอนข้อมูลหลายเมกะไบต์ผ่านเน็ตทุกครั้งที่เปิดหน้า

แบบเดียวกันนี้เกิดที่ `getBillingRoundsHistory`, `getCompletedBillingRounds` และ `computeJobStatusReportRows` (ตัวหลังดึง 4 ตารางเต็ม ๆ พร้อมกันมาต่อกันในหน่วยความจำ)

**ทางแก้ที่ถูกต้อง:** ให้ Postgres สรุปยอดมาให้เลย (สร้าง view) แทนที่จะดึงดิบมาสรุปเองในโค้ด — จาก 27,000 แถวเหลือ ~150 แถว

ยังไม่ได้ทำในรอบนี้ เพราะเป็นการเปลี่ยนตรรกะการคำนวณยอดเงิน ควรทำหลังเห็นตัวเลขจริงจากไฟล์ตรวจสุขภาพก่อน จะได้ทดสอบเทียบยอดเก่า/ใหม่ได้ว่าตรงกัน

## 🟡 4. ไฟล์ใน Storage ไม่เคยถูกลบ และไม่จำกัดขนาด

ไฟล์ที่ผู้รับเหมาส่งกลับถูกเก็บถาวรใน Storage และ **ไม่มีที่ไหนในโค้ดลบไฟล์เลย**

ประเมินจากไฟล์ตัวอย่างที่ส่งมา (0.73 MB ต่อ 1 ใบงาน 14 รูป) — ฟอร์มใหม่มี 22 ช่องรูป + ใบ JOB ORDER จึงน่าจะราว 1-1.5 MB ต่อใบ

```
200 งาน/เดือน × 36 เดือน × ~1.2 MB  ≈  10 GB ที่ 3 ปี
```

ยังไม่ถึงขั้นวิกฤต แต่มี 2 จุดที่ควรแก้:

- **ไม่มีการจำกัดขนาดไฟล์อัปโหลด** — ค้นในโค้ดแล้วไม่เจอเลย ถ้าผู้รับเหมาส่งไฟล์ 200 MB มาก็รับไว้หมด
- **ไฟล์กำพร้า** — ตอนลบประวัติด้วย SQL ตัวไฟล์จริงยังค้างอยู่ (เขียนเตือนไว้แล้วในไฟล์ `ลบประวัติฟอร์มที่ผู้รับเหมาส่งกลับ.sql`) บล็อก 6 ในไฟล์ตรวจสุขภาพจะบอกว่ามีกี่ไฟล์และกินที่เท่าไหร่

## 🟡 5. วันที่เก็บเป็นข้อความ ไม่ใช่ชนิดวันที่

`req_date` และ `fix_date` เก็บเป็นข้อความรูปแบบ `DD/MM/YYYY` ไม่ใช่ชนิด `date` ของ Postgres

ผลที่ตามมา: **กรองช่วงวันที่ใน SQL ไม่ได้** ต้องดึงทั้งตารางออกมากรองในโค้ดแทน — นี่คือต้นตอที่ `generateBillingRound` ต้องดึงทุกแถวใน `close_issues` ทุกครั้งที่จับคู่รอบบิล และเป็นเหตุผลที่ข้อ 3 แก้ยาก

นอกจากนี้ยังทำให้เรียงวันที่ผิดด้วย (`'01/12/2026'` มาก่อน `'02/01/2026'` เมื่อเรียงแบบข้อความ)

**ทางแก้:** เพิ่มคอลัมน์ชนิด `date` คู่ขนานไปกับคอลัมน์ข้อความเดิม ให้ระบบเขียนทั้งสองช่อง แล้วค่อยย้ายมาใช้ช่องใหม่ทีละจุด — ทำได้โดยไม่กระทบข้อมูลเดิมและไม่ต้องหยุดระบบ

## ✅ เรื่องที่ตรวจแล้วไม่มีปัญหา

- **การแบ่งหน้าใน `downloadAllBillingXlsx`** — ทำถูกแล้ว ดึงทีละ 1,000 แถวจนหมด เป็นแบบอย่างที่ควรใช้กับจุดอื่น
- **`branch_assets` (39,186 แถว)** — ตารางใหญ่สุดในระบบ แต่มีดัชนีครบและค้นด้วยรหัสสาขาเสมอ ไม่มีปัญหา
- **`asset_warranty` (54,866 แถว)** — เป็นข้อมูลนิ่ง ไม่โต และค้นด้วยเลขทรัพย์สินเฉพาะเจาะจง
- **`getJobFormSubmissions`** — มี `.limit(500)` กำกับไว้แล้ว ไม่ระเบิด
- **การตัดบิล** — เงื่อนไข `sent_to_contractor = true AND completed_at is null` รัดกุมดี ไม่ตัดข้ามรอบ

## ลำดับที่ควรทำ

**ขั้นที่ 1 — วัดของจริงก่อน (วันนี้)**

รัน `ตรวจสุขภาพระบบ-รองรับ3ปี.sql` ทั้ง 8 บล็อก (อ่านอย่างเดียว ปลอดภัย 100%) แล้วส่งผลกลับมา พร้อมค่า **Max rows** จาก `Settings → API`

**ขั้นที่ 2 — เพิ่มดัชนี (ทำได้เลย ไม่ต้องรอ)**

รัน `เพิ่มดัชนี-รองรับ3ปี.sql` — ไม่แตะข้อมูล ไม่ต้อง deploy ไม่ต้อง build แอปใหม่ ได้ผลทันที

**ขั้นที่ 3 — แก้โค้ดตามตัวเลขที่วัดได้**

พอเห็นตัวเลขจริงแล้วจะรู้ว่าต้องแก้แค่ไหน เรียงตามความคุ้ม:

1. ใส่การแบ่งหน้าให้ 15 จุดที่ดึงทั้งตารางแบบไม่มีเงื่อนไข (แก้ข้อมูลหายเงียบ ๆ)
2. ทำ view สรุปยอดให้ 3 ฟังก์ชันที่ดึงทั้งตารางมานับ (แก้ความช้า)
3. จำกัดขนาดไฟล์อัปโหลด + เครื่องมือล้างไฟล์กำพร้า
4. เพิ่มคอลัมน์วันที่ชนิด `date`

ทั้ง 4 ข้อทำแยกกันได้ ไม่ต้องทำพร้อมกัน บอกได้ว่าจะเริ่มข้อไหนก่อน
